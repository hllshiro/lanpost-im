# 文件传输状态机与故障排查

当前文件传输只使用 IPMSG 兼容通道：UDP 发邀请，TCP 拉取文件。没有实现内网通私有 ENet 文件通道，也没有实现文件夹传输。

## 流程

1. 发送方通过 UDP 2425 发送 `SENDMSG | SENDCHECK | FILEATTACH`，报文序号就是 `packetId`。
2. 接收方回 `RECVMSG`，版本 `1@shiyeline`，正文是十进制 `packetId` 加 NUL。
3. 接收方建立 TCP 连接，连到发送方的文件服务端口（默认 2425）。
4. 接收方发送 `GETFILEDATA(0x60)`，版本 `1`，扩展域为 `packetId:fileId:offset:`，全部十六进制。
5. 发送方按任务匹配后返回原始文件字节，接收方按附件表大小写入文件。

## 发送方状态

| 状态           | 进入条件                            | 说明                            |
| -------------- | ----------------------------------- | ------------------------------- |
| `offered`      | 邀请发出、任务登记完成              | 等待对端接收并拉取              |
| `transferring` | 首次匹配到 `GETFILEDATA` 并开始写流 | 收到任何字节前也可能短暂显示 0% |
| `done`         | TCP 文件流完整发送                  | `received` 应等于文件大小       |
| `failed`       | 打开、读取或写入文件失败            | `error` 记录具体原因            |
| `canceled`     | 用户取消                            | 不再接受新的拉取请求            |

发送方不会因为收到 `RECVMSG` 就进入 `transferring`。`RECVMSG` 只说明对端收到了邀请，真正开始传输以 TCP 拉取为准。

## 接收方状态

| 状态           | 进入条件                     | 说明                       |
| -------------- | ---------------------------- | -------------------------- |
| `waiting`      | 收到附件邀请                 | 等待用户接收或自动接收策略 |
| `transferring` | 用户接收，发出确认并开始拉取 | 排队期间也显示在传输中     |
| `done`         | 文件字节数等于附件大小       | 路径写入数据库             |
| `rejected`     | 用户拒绝                     | 只更新本地状态             |
| `failed`       | 连接、读取或写盘失败         | 半截文件会被删除           |
| `canceled`     | 用户取消                     | 中止拉取                   |

## 任务匹配

发送方按以下顺序匹配 `GETFILEDATA`：

1. `packetId` 相同，并且 TCP 来源 IP 与邀请对端 IP 相同。
2. 附件文件 ID 匹配。
3. 该对端最新的 `offered` 或 `transferring` 任务。

第 3 条是真实内网通的兼容兜底。部分版本会回传自己的任务标识或文件句柄，前两种都匹配不上；如果没有兜底，服务端会关闭连接，双方会一直停留在等待状态。

同一对端同时有多个待发送任务时，兜底可能选到最新的任务。正常的 packetId 匹配会优先命中；出现多个文件同时等待且对端标识异常时，需要按日志确认实际服务的是哪一个任务。

## 常见故障

| 现象                                            | 优先检查                            | 处理                                                                                |
| ----------------------------------------------- | ----------------------------------- | ----------------------------------------------------------------------------------- |
| 对方显示等待建立链接，本机没有 `收到取文件连接` | 入站 TCP 2425、防火墙、安全软件     | 放行当前 `electron.exe` 或打包后的 `lanpost-im.exe`；开发版和安装版是不同可执行文件 |
| 有连接日志，但出现 `忽略未知的取文件请求`       | 版本、字段、packetId、seq           | 确认 `GETFILEDATA` 版本是 `1`，扩展域是十六进制冒号格式，seq 没有超过 32 位         |
| 对端返回 0 字节                                 | 请求版本、包编号、seq               | 带 `@shiyeline` 的版本会被拒绝；包编号不匹配也会直接关闭                            |
| 发送方一直 `offered`，接收方一直等待            | TCP 没有到达，或匹配失败            | 先看连接日志；没有连接查网络/防火墙，有连接查未知请求日志                           |
| 文件传输到一半失败                              | TCP 超时、写盘失败、对端提前关闭    | 检查 `error`，确认接收目录可写，确认文件大小                                        |
| 文件完整但内容不对                              | 保存了错误的 TCP 响应或覆盖了旧文件 | 用 SHA-256 对比源文件和接收文件                                                     |
| 拒绝后发送方仍显示等待                          | IPMSG 没有标准拒绝报文              | 这是协议限制，发送方只能停在 `offered`                                              |
| 同名文件重复                                    | 接收目录已有文件                    | 自动生成 `名称 (1).扩展名`                                                          |

## 关键约束

- 端口 2425 同时承载 UDP 和 TCP；修改端口或监听地址后必须重启。
- `GETFILEDATA` 的 TCP 端口和 UDP 端口相同，默认 2425。
- 未知包编号、版本错误、报文头无法解析时，服务端关闭连接，不返回错误正文。
- 接收目录由 `files.receiveDir` 决定；留空时使用 `Downloads\内网传书`，不可写时回退到 `<userData>\recv`。
- 修改接收目录后需要重启文件服务。
- 拒绝不会回传发送方，发送方任务不会自动变成 `rejected`。
- 文件夹传输和私有 ENet 文件通道不在当前实现内。

## 调试入口

- 日志：`startup.log` 中的 `收到取文件连接`、`忽略未知的取文件请求`、`文件服务启动`。
- 代码：`src/main/files/manager.ts`（任务、匹配、状态）、`server.ts`（TCP 请求与流）、`client.ts`（拉取）、`src/main/app-service.ts`（发送、接收、事件）。
- 协议：`src/main/protocol/discovery.ts` 的 `sendFileOffer`、`sendFileAccept`、`handshakeMessage`。
- 测试：`pnpm exec vitest run src/main/files src/main/protocol`。
- 抓包和报文：`docs/protocol-debugging.md`。
