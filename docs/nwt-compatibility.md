# 内网通兼容矩阵与私有通道

目标对端是真实内网通 3.4.3055。当前客户端只走 2425 上的 IPMSG 兼容通道；内网通的 9011/ENet 私有通道没有实现，也不应该和兼容通道混用。

## 兼容矩阵

| 能力                   | 真实内网通 ↔ 本客户端 | 本客户端 ↔ 本客户端 | 说明                                                                                              |
| ---------------------- | --------------------- | ------------------- | ------------------------------------------------------------------------------------------------- |
| 上线、下线、联系人发现 | 可用                  | 可用                | `BR_ENTRY(1)` / `ANSENTRY(3)`，心跳 1016，120 秒离线                                              |
| 分组、昵称、状态、签名 | 可用                  | 可用                | Entry 正文和 `X_CHANGE_STATUS` / `X_CHANGE_SIGN`                                                  |
| 文字消息               | 可用                  | 可用                | 对真实内网通固定走 `SENDMSG(32)` 与 `SENDCHECK(0x100)`；双方完成私有握手后才用 `X_SEND_MSG(1004)` |
| 文字送达确认           | 可用                  | 可用                | `RECVMSG(33)`，正文是十进制包序号加 NUL，版本 `1@shiyeline`                                       |
| 文件邀请               | 可用                  | 可用                | `SENDMSG`、`SENDCHECK`、`FILEATTACH(0x200000)`，正文后接附件表                                    |

| 共享文件柜             | 未实现                | 未实现              | 私有 5000–5009                                                                                    |
| 远程协助               | 未实现                | 未实现              | 私有 4000+，依赖 `Remote.dll`                                                                     |
| 离线消息               | 未实现                | 未实现              | 内网通无服务器版本的离线能力未接入                                                                |
| 文件夹传输             | 未实现                | 未实现              | 未实现 `GETDIRFILES`/目录附件                                                                     |
| IPMSG 加密             | 未实现                | 未实现              | 当前消息在局域网内明文传输                                                                        |

## 必须保持的兼容细节

- 真实内网通的标准报文也使用 `1@shiyeline` 头，但它不会完成私有聊天握手。版本后缀不能作为“支持 `X_SEND_MSG`”的判断依据；只有 `peer.ready` 为真时才走私有 XML。
- 私有握手会声明文件端口。只实现 TCP 文件传输时：
  - `FILE_TRAN_TCP_PORT` 设为实际监听端口（默认 2425）。
  - `FILE_TRAN_ENET_PORT` 必须设为 0。
  - 广告一个有效的 ENet 端口会让对端选择私有 UDP 通道，然后一直等待我们并未实现的连接。
- 文件拉取请求的版本必须是 `1`，不能带 `@shiyeline`。扩展域是 `packetID:fileID:offset:`，全部十六进制，结尾带冒号。
- 真实内网通可能回传自己的文件标识。发送端匹配顺序是 packetID + 对端 IP、文件 ID、该对端最新的 `offered`/`transferring` 任务；最后一种是为兼容对端标识不一致准备的兜底。
- 文件邀请和文字都优先使用 GBK；只有 GBK 不可用时才使用 UTF-8 并设置 `IPMSG_UTF8OPT(0x800000)`。
- 广播 `BR_ENTRY` 的头部是 `1@shiyeline`，种子单播使用版本 `1`；抓包时不要只过滤版本 `1`。

## 私有通道结论（未实现）

内网通的私有通道和 2425 兼容通道是两套机制：

- 9011/UDP 上是 304 字节的二进制发现报文，类型 1/2，包含 IP、端口、企业标识和两个 65 字节块；完整校验条件还没有还原。
- 发现后建立 ENet 可靠 UDP 会话，使用临时端口；命令字节与 ENet 的 CONNECT、VERIFY、SEND_RELIABLE、SEND_FRAGMENT 一致。
- ENet 载荷封装为 `uint32 长度 + uint32 命令号 + 16 字节随机块 + 载荷`。
- 1000/1004/3011 等控制载荷熵约 7.4–7.8，二进制里有 AES 查表，疑似使用 AES 流模式加密；使用企业标识、候选密钥、MD5/SHA 派生和常见模式都没有解出明文。这是私有通道的主要阻塞点。
- 私有文件的数据通道是明文，帧格式为 `uint32 长度 + uint32 版本/类型 + uint32 子类型 + 载荷`，端口由私有报文协商，不固定是 9012–9014。控制层没有解密之前，无法完成私有文件协商。
- 群组、共享文件柜、远程协助和私有文件都依赖这条通道；在私有控制层可用之前不要广告 ENet 端口，也不要用 `X_SEND_MSG` 代替兼容文字。

## 验证方式

- 真实内网通回归重点：发现、文字、文字回执、双向文件、文件拒绝表现。
- 文件发送方看 `startup.log` 是否有 `收到取文件连接: IP:端口`；没有这一行说明 TCP SYN 没有到达文件服务，优先查防火墙或安全软件入站规则。
- 有连接但出现 `忽略未知的取文件请求` 时，检查 `GETFILEDATA` 的版本、十六进制字段和 32 位 seq。
- 抓包和报文示例见 `docs/protocol-debugging.md`，标准协议见 `docs/ipmsg-protocol-zh.md`。
