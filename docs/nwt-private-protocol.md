# 内网通私有协议（文字消息）

本文描述本客户端实现的内网通私有通道，范围限文字收发。协议的逆向过程、抓包原始字节和样本地址索引在 `../../nwt-re/docs/private-protocol.md`，本文按实现者和维护者的视角组织。

- 对端：内网通 3.4.3055（Windows）
- 状态：文字收发已与本机样本和另一台真实客户端联调通过
- 不在本文范围：私有文件、群组、共享文件柜、远程协助、离线消息

## 1. 两套通道的分工

客户端同时具备两套互通方式：

| 通道 | 端口 | 用途 |
|---|---|---|
| IPMSG 兼容层 | UDP/TCP 2425 | 飞鸽、飞秋、内网通的标准文字与文件 |
| 内网通私有通道 | UDP 9011 + 临时 UDP 端口 | 私有握手、文字、已读回执 |

默认两套都开。私有会话就绪时文字走私有通道，否则走 IPMSG；设置里关闭 `network.ipmsg` 后只保留私有通道，2425 不再绑定，文件发送不可用。

## 2. 端口

| 端口 | 协议 | 说明 |
|---:|---|---|
| 9011 | UDP | 发现报文；客户端只监听和解析，不发送通告 |
| 系统分配 | UDP | ENet 会话，监听端口由 `bind(0)` 决定 |
| 9012 | UDP | 对端（真实内网通）的 ENet 监听端口，抓包里常见的连接目标 |

私有会话的本地端口是临时的，对端通过我们发出的 CONNECT 源端口回包；对端自己的 ENet 端口来自它的 9011 通告，或在设置 `network.privateSeeds` 里写死 `IP` 或 `IP:9012`。

## 3. 发现报文（9011/UDP，304 字节）

类型 1 是通告，类型 2 是应答。客户端解析以下字段，其余忽略：

| 偏移 | 长度 | 含义 |
|---:|---:|---|
| 0x00 | 4 | 总长，大端，固定 304 |
| 0x04 | 4 | 类型：1 通告、2 应答、4 会话 hello |
| 0x08 | 4 | 版本，固定 1 |
| 0x0c | 4 | 固定值 `0x5FC1D8EC`，样本用 `cmp` 校验，填当前时间会被拒绝 |
| 0x10 | 4 | 本机 IPv4 |
| 0x14 | 4 | 网段广播地址 |
| 0x1a / 0x1c | 2 | 端口 9012 |
| 0x1e | 65 | 32 位十六进制用户标识 + 0 填充 |
| 0x5f | 65 | 16 字节随机标识 + 0 填充 |
| 0xa0 | 4 | 固定值 500 |
| 0xa5 | 2 | ENet 端口，大端 |

客户端收到类型 1/2 且 `enetPort > 0` 的报文时，记录 `IP → ENet 端口` 并对该地址建立会话。报文自带 IP 字段不参与路由，一律用 UDP 源地址。

## 4. ENet 会话

字段一律大端。

### 4.1 数据报与命令

```
u16 peerID（0x8000 = 带 sentTime，0x3000 = 会话号，0x0fff = 对端编号）
u16 sentTime（peerID 最高位为 1 时存在）
重复：u8 命令 | u8 通道 | u16 可靠序号 | 载荷
```

命令字的低 7 位是 ENet 命令，最高位 0x80 表示要求 ACK：

| 字节 | 命令 | 载荷 |
|---:|---|---|
| 0x01 | ACK | `u16 被确认序号 + u16 对端 sentTime`（4 字节） |
| 0x02 | CONNECT | 44 字节，见下 |
| 0x03 | VERIFY_CONNECT | 40 字节，见下 |
| 0x04 | DISCONNECT | 4 字节 |
| 0x05 | PING | 空 |
| 0x06 | SEND_RELIABLE | `u16 长度 + 数据` |
| 0x08 | SEND_FRAGMENT | `u16 起始序号、u16 本片长度、u32 分片总数、u32 分片序号、u32 总长、u32 偏移、数据` |
| 0x0a | BANDWIDTH_LIMIT | 8 字节 |

CONNECT 载荷：`u16 outgoingPeerID、u8 incomingSessionID、u8 outgoingSessionID`（新连接时两个会话字节都填 0xff），随后 10 个 u32：MTU 1400、窗口 65536、通道数 1、两个带宽 0、throttle 参数 5000/2/2、connectID、data 0。

VERIFY_CONNECT 载荷：`u16 对端编号、u8 incomingSessionID、u8 outgoingSessionID`，随后与 CONNECT 相同的 u32 序列，但不含末尾 data。两个会话字节由接收侧选定。

### 4.2 会话号

VERIFY_CONNECT 载荷第 2、3 字节是 ENet 会话号（实测 0–3，随连接变化）。客户端作为发起方采用其中的 `outgoingSessionID`，作为接收方固定选 1。之后每个出站数据报头的第 12–13 位必须写这个会话号，写 0 会被对端丢弃并重传 VERIFY_CONNECT。

### 4.3 可靠性

- 通道 0 维护 16 位自增序号，序号从 1 开始，两端必须一致。
- 未确认命令 500ms 起步、1.5 倍退避重传，6 次后丢弃；丢弃时回调上层，由上层把消息状态置 `failed`。
- ACK 只有当 `(可靠序号, 数据报 sentTime)` 两个字段都匹配时才清除未确认项。
- 接收端按 16 位序号比较规则（`(a - b) & 0xffff < 0x8000`）按序交付，乱序先缓存。
- 收到要求 ACK 的命令先校验再回 ACK；校验失败的命令不 ACK，由对端重传，避免把一条坏命令之后的整条流卡死。
- 分片按 `起始序号 + 偏移` 重组；单条消息上限 1 MiB，分片数上限 820，未收齐的分片组 30 秒过期、最多同时缓存 8 组。
- 通道内单条消息超过 1280 字节时自动用 SEND_FRAGMENT 拆分。

### 4.4 超时与重连

- 发起方 5 秒收不到 VERIFY_CONNECT 就重发 CONNECT，最多 3 次。
- 接收方回 VERIFY_CONNECT 后，500ms 起步、最多 6 次重发，直到收到 ACK，或收到对端任意可靠负载（说明对端已收到 VERIFY）。
- 会话就绪后每 30 秒发一次 `X_HEARTBEAT`，120 秒没有任何入站报文判定超时并关闭。
- 关闭时发 `X_QUIT`（1017），收到 DISCONNECT（0x04）直接关闭。
- 双方同时发起时按确定性规则只保留一个方向：先比较本端与对端 IPv4 的数值，相同再比较本端 ENet 端口与会话远端端口，较大的一方放弃出站会话、改为接收侧；另一方忽略对方的 CONNECT，保留自己的 connectID。
- 对端用新的 connectID 重新连接时，按同一规则重建会话；同一 connectID 视为重传，只重发 VERIFY_CONNECT。

## 5. 应用帧与加密

```
u32 总长（大端，等于 8 + 正文字节数）
u32 命令号（大端）
正文（UTF-8 XML，TEA 密文）
```

正文加密规则：

- 算法：TEA，32 轮，delta `0x9e3779b9`。
- 密钥：`8asfhj@k7*20hbla`（16 字节 ASCII），样本 `.rdata` 0x9ef1c8。
- 字节序：8 字节块与四个密钥字都按大端解释，输出按大端写回。
- 分组：从正文第一个字节开始每 8 字节独立加密，末尾不足 8 字节的部分保持明文。

心跳 `<X_HEARTBEAT docver="1" />`（26 字节）加密后是 3 个密文块加末尾 `2f 3e`（`/>`）：

```
d529c5439de045c9 d3dc11866769e1fe dfa896e8e704a553 2f3e
```

## 6. 消息

会话建立后先发 304 字节、类型 4 的 hello（明文，结构同发现报文），再交换以下 XML。所有 XML 带 `docver="1"`。

| 命令 | 名称 | 方向 | 说明 |
|---:|---|---|---|
| 4 | hello | 双向 | 304 字节，`[u32 304][u32 4][报文]`，不经应用帧加密 |
| 1000 | X_HANDSHARK | 双向 | 能力位、个人资料、端口 |
| 1004 | X_SEND_MSG | 双向 | 文字，`<MSG>` 内是 JSON |
| 1005 | X_SEND_MSG_ACK | 收→发 | 送达确认，带 `MSG_ID` |
| 1006 | X_SEND_RECEIPT | 收→发 | 已读回执，带 `MSG_ID` |
| 1008 | X_SEND_WRITTING | 双向 | 正在输入，客户端只记日志 |
| 1016 | X_HEARTBEAT | 双向 | 心跳 |
| 1017 | X_QUIT | 双向 | 退出 |
| 1018 | X_READY | 双向 | `USER_ID` 为本机 32 位十六进制标识 |

`X_HANDSHARK` 只声明 `MSG=2:1` 与 `HIDE_RECORD=1`，其余能力位与 NET 端口为 0，避免对端发起未实现的私有文件流程；`<INFO><GROUP>` 不能为空或纯空白，空值按 `Default` 发送，否则对端回 DISCONNECT。

### 6.1 文字 JSON

`X_SEND_MSG` 的 `<MSG>` 内是 JSON，空格写成 `&nbsp;`、引号写成 `&quot;`：

```json
{
   "app" : "shiyeline",
   "dt" : [
      {
         "txt" : {
            "t" : "normal",
            "v" : "你好"
         }
      }
   ],
   "ft" : {
      "b" : "0",
      "c" : "0x000000",
      "i" : "0",
      "n" : "微软雅黑",
      "s" : "9",
      "u" : "0"
   },
   "id" : "cb4b27c771da884caaa0622b2912d574",
   "type" : "0",
   "ver" : "6.0"
}
```

接收时按 `dt` 数组逐项取文字：`txt.v` 是正文，`lnk.v` 是链接地址，`img` 节点显示 `[图片]`，`file` 节点显示 `[文件]`；其它节点忽略。没有任何可显示内容的 `1004` 仍回 1005，但不入库。

发送固定写 `RECEIPT=0`、`MSG_TIME=0`、`OFFLINE=0`、`HIDE_RECORD=0`，`MSG_ID` 用毫秒时间戳加三位自增。

## 7. 会话时序

```
发起方                         接收方
  |-- CONNECT (connectID) ------->|
  |<-- VERIFY_CONNECT (peerID, ---|
  |    sessionID, connectID)      |
  |-- ACK + PING ---------------->|
  |-- hello (304B, 明文) -------->|
  |-- X_HANDSHARK (TEA) --------->|
  |<-- hello ---------------------|
  |<-- X_HANDSHARK (TEA) ---------|
  |<-- X_READY -------------------|
  |-- X_READY ------------------->|
  |== 1004 / 1005 / 1006 / 1016 ==|
```

握手完成后 `sendText` 才走私有通道。对端先发 `X_READY`、后发 `X_HANDSHARK` 时，握手资料以 `X_HANDSHARK` 为准，客户端在收到资料时登记联系人，不依赖 `X_READY` 的先后。

## 8. 客户端实现

### 8.1 模块

```
src/main/protocol/private/
  tea.ts        TEA 加解密
  frame.ts      应用帧编解码
  enet.ts       ENet 报文编解码、可靠通道、分片、ACK
  beacon.ts     9011 发现报文与 hello 编解码
  messages.ts   私有 XML 与文字 JSON
  session.ts    单对端会话状态机
  service.ts    多对端服务：套接字、种子、发现、pump
  route.ts      路由与回执的纯函数（消息号、通道选择、待回执筛选、超时判定）
```

`AppService` 负责编排：连接私有多对端服务、决定每条文字走哪条通道、把收发的消息写库、把 1005/1006 映射成消息状态、在 `markRead` 时补发已读回执。

### 8.2 设置

| 设置 | 默认 | 说明 |
|---|---|---|
| `network.ipmsg` | `true` | 关闭后只启用内网通私有协议，2425 不再绑定 |
| `network.privatePort` | `9011` | 发现报文监听端口 |
| `network.privateSeeds` | `[]` | `IP` 或 `IP:ENet端口`，广播不可达时直连 |
| `identity.privateId` | 首次启动生成 | 32 位十六进制私有用户标识 |

### 8.3 发送与状态

- 目标联系人有就绪的私有会话时，文字走 `X_SEND_MSG`；否则走 IPMSG。关闭 `network.ipmsg` 后，没有就绪会话就报“内网通私有会话未就绪”。
- 只在私有通道出现过的联系人没有 IPMSG 端口，回落 IPMSG 会丢包，因此直接报“联系人不在线”。
- 交给私有通道的消息在 30 秒内没有 1005/1006，或重传耗尽、会话关闭时，状态置 `failed`，不跨通道重发。
- 1005 置 `delivered`，1006 置 `read`；迟到的 1005 不会把 `read` 降回 `delivered`。
- `markRead` 对水位线以内、尚未回过执的私有入站消息逐条发 1006。

### 8.4 联系人身份

同一个人可能分别由 IPMSG 和私有通道提供身份。客户端维护 `IP → 联系人 key` 的映射，启动时从数据库载入（同一 IP 取最近使用的 key），两条通道都复用同一个 key；私有身份使用握手里的 `CORP_ID`，IPMSG 身份使用账号。这样不会因为哪条通道先到达而出现两个同名联系人。

## 9. 实测差异与坑

以下细节只有接真实客户端才会暴露，均已实现并有测试：

- ENet 会话号必须回填到之后每个数据报的头部，否则对端丢弃你的 ACK、hello 和心跳。
- ACK 的命令头通道号必须等于被确认命令所在的通道：握手命令用 0xff，hello 与业务命令用 0。
- hello 的 0x0c 是固定常量 `0x5FC1D8EC`，不是时间戳；填当前时间会被回 DISCONNECT。
- `X_HANDSHARK` 的 `<GROUP>` 为空或纯空白会被回 DISCONNECT。
- 对端会发 DISCONNECT（0x04），解码器必须认识它，否则整条数据报被当成坏包丢掉。
- 文字里的链接是 `dt[].lnk`，不是 `txt`；只取 `txt` 会把链接消息当成空消息。

## 10. 已知限制

- 私有文件、文件夹、群组、共享文件柜、远程协助、离线消息未实现；关闭 IPMSG 后文件发送不可用。
- 客户端不发送 9011 通告，只监听；对端必须自己广播发现报文，或者用 `privateSeeds` 直连。
- 私有一对一会话的失败重发只在本通道内进行，不跨通道重发。
- 9011 发现报文的准入条件（0xa9 起的功能字段）还没有完全还原，伪造通告不会被真实客户端接受，因此本客户端只做接收侧。
- 正在输入（1008）只记日志，不展示。
